# Аудит и архитектура админ-панели heradeLegend

Дата аудита: 2026-10-10  
Репозиторий: https://github.com/WhiteBelStudio/Hereid  
Ветка: `main`

## 1. Состояние репозитория

Проверены корень репозитория, `main.py`, `start.py`, `requirements.txt` и `README.md`.

- Бот написан на Python с aiogram 3 и SQLite.
- `main.py` содержит около 500 строк и объединяет обработчики Telegram, модерацию, SQL и клавиатуры.
- `start.py` устанавливает зависимости и запускает бота; текущую схему запуска менять не требуется.
- Уже есть команды модерации: бан/разбан, мут/размут, предупреждения и выговоры.
- База создаётся автоматически. Существующие таблицы: `warnings`, `reprimands`, `actions`.
- Уже есть простое inline-меню администратора, справка и счётчик действий.
- Полноценной системы ролей/разрешений, редактируемого каталога RP-действий и настроек по чатам в текущей схеме не обнаружено.
- Отдельного набора автоматических тестов в корне репозитория не обнаружено.
- В проекте предусмотрены `BOT_TOKEN`, `DB_PATH`, `LOG_LEVEL`, а также необязательные параметры прокси и таймаута Telegram.

## 2. Важные замечания аудита

1. Проверка прав при входе в раздел «Администратор» есть, но остальные callback-разделы («Команды», «Статистика» и т. п.) не используют единый общий guard. До расширения панели необходимо централизовать авторизацию для каждого административного callback.
2. Текущие права основаны на статусе администратора Telegram-группы. Это не заменяет внутренние роли бота: владелец, администратор, модератор и помощник.
3. Существующие таблицы и файл базы нельзя удалять или пересоздавать. Новые таблицы нужно добавлять совместимо через `CREATE TABLE IF NOT EXISTS` или отдельные безопасные миграции.
4. Настройки и действия должны быть привязаны к `chat_id`, чтобы конфигурация одной группы не меняла другую.
5. Необходимо продолжить проверку сетевого подключения отдельно: успешность аудита кода не означает, что бот смог подключиться к Telegram. В истории запуска уже наблюдалась проблема доступности Telegram через прокси.

## 3. Минимальная архитектура без лишнего усложнения

- **`main.py`** — текущие команды, запуск и подключение обработчиков; не переписывать целиком.
- **`admin_panel.py`** — меню панели, callback-навигация и интерфейс управления.
- **`permissions.py`** — единая проверка внутренних ролей и разрешений.
- **SQLite** — добавить таблицы ролей/назначений, RP-действий/ключевых слов, настроек чатов и аудита; сохранить текущие таблицы.
- **Тесты** — проверить права, сохранение настроек и ключевые сценарии до публикации изменений.

Новые модули добавлять только по мере необходимости. Не вводить отдельный API, веб-панель, ORM или сложную систему миграций для текущего небольшого бота.

## 4. Порядок реализации после аудита

1. Закрыть все административные callback единым контролем прав.
2. Реализовать роли и разрешения с владельцем, которого нельзя снять через обычную панель.
3. Добавить управление RP-действиями и ключевыми словами без команд со слешем.
4. Добавить настройки по чатам и базовые антиспам-ограничения.
5. Добавить журнал изменений и минимальную статистику.
6. Добавить тесты, проверить совместимость с существующей SQLite-базой и инструкции запуска.
